# Страница

Страница LiveView — это ящик для входящих. Она не решает, что показать. Она смотрит, откуда пришло сообщение, и зовёт модуль, который за этот вход отвечает.

| Откуда пришло | Куда уходит | Что это |
| --- | --- | --- |
| `mount` | `Request.boot` | страница только открылась |
| `handle_event` | `Event` | человек нажал или ввёл |
| `handle_async` с `{:ok, _}` | `Request.loaded` | запрошенные данные пришли |
| `handle_async` с `{:exit, _}` | `Request.failed` | запрос не удался |
| `handle_info` | `Screen.deliver` | данные пришли сами, страница их не просила в этот момент |

`handle_async` и `handle_info` в файле страницы не пишутся. Их подставляет `use AssistantWeb.Shared.Page`: ответ запроса уходит в соседний `Request`, само пришедшее сообщение — в соседний `Screen`. На странице остаются `mount` и события человека.

Шаблон страницы только раскладывает компоненты. Компонент рисует то, что ему передали, и сам ничего не читает из базы.

`@messages` в шаблоне — это память процесса этой страницы (`socket.assigns`). Браузер получает готовую вёрстку, а не список сообщений.

## Screen

Состояние открытого экрана: какой чат выбран, что лежит в журнале, какая фаза ответа, что написано в поле и есть ли ошибка.

`open` переключает чат. Отписывается от старого, подписывается на новый, очищает журнал и фазу и запускает их чтение. И клик по чату, и первая загрузка списка идут через `open`, поэтому переключение описано один раз.

`reset` ставит начальные значения экрана. `put_messages` и `put_phase` записывают уже полученное. Если фаза уже успела обновиться более свежим сообщением, поздний ответ чтения её не затирает.

`deliver` принимает то, что пришло по подписке: список чатов изменился, сменилась фаза, пришёл ход, пришёл кусок ответа, пришла ошибка. Изменение списка чатов отсюда уходит в повторное чтение: само чтение остаётся делом `Request`.

`reason` переводит причину отказа в текст на экране.

Чтение сообщений и фазы стартует в `Screen.open`, а ответ всё равно обрабатывает `Request`. Открытие чата — переход экрана, и его должны уметь сделать и клик, и загрузка списка. Разбор ответа — отдельная граница: это результат запроса.

## Event

Только действия человека.

`draft` запоминает текст в поле и снимает прошлую ошибку. `send` отдаёт текст в `Assistant` и либо очищает поле, либо показывает причину. `select` открывает другой чат. Повторный выбор уже открытого чата ничего не делает, чтобы журнал не мигал загрузкой.

Страница до вызова приводит значение из браузера к нужному типу. Для выбора чата это перевод id из строки в число. Смысл действия решает уже `Event`.

## Request

Чтение, которое страница запросила сама. У каждого чтения есть имя: `:chats`, `:messages`, `:phase`. По этому имени ответ попадает в свою ветку.

`boot` готовит первый экран: подписка на изменения списка чатов, пустое состояние, старт чтения списка. `reload` перечитывает список. `loaded` раскладывает успешный ответ, `failed` — ошибку.

Если журнала ещё нет, при чтении списка создаётся один чат. Если фазу прочитать не удалось, экран считает её свободной, чтобы поле ввода не осталось заблокированным.

Пока идёт первое чтение, на экране состояние загрузки. Мёртвый первый рендер (ещё без сокета) тоже его показывает: само чтение выполняется уже на живом соединении.

## Log

Чистые операции над списком сообщений: добавить ход, склеить прочитанный журнал с тем, что уже успело прийти, дописать кусок ответа. Сокета здесь нет и обращений к `Assistant` тоже нет.

## Компонент

Функция с шаблоном рядом: `chat_list/chat_list.ex` и `chat_list.html.heex`. Страница передаёт ему готовые данные. Общий компонент, который нужен двум фичам, живёт в `shared`. Компонент одной фичи остаётся в `features/<фича>/components`.
